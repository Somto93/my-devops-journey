# Module 1 - Linux Infrastructure Baseline and Recovery

**Project:** Three-VM, two-tier e-commerce homelab  
**Platform:** CentOS Stream 10, VirtualBox  
**Repository:** `my-devops-journey`  
**Outcome:** Baseline captured, recovery snapshots created, cloned machine IDs corrected, and application connectivity validated.

## 1. Project objective

Establish a reproducible baseline of a three-VM Linux environment before further DevOps exercises. Document compute, memory, storage, packages, services, networking, routing, firewall, recovery checkpoints, and system identity. Validate that a maintenance change does not disrupt the deployed e-commerce application.

## 2. Architecture

```text
Windows host (host-only network 192.168.56.0/24)
  |-- lab-server-1: 192.168.56.10 (web)
  |-- lab-server-2: 192.168.56.20 (database)
  `-- lab-router:   192.168.56.30 (router)

lab-server-1                   lab-router                    lab-server-2
192.168.10.10/24  ---->  192.168.10.1 | 192.168.20.1  ----> 192.168.20.10/24
Apache + PHP-FPM             IPv4 forwarding/firewalld        MariaDB :3306
                                    |
                             NAT 10.0.5.15/24
                             gateway 10.0.5.2
```

The web and database VMs have default gateways `192.168.10.1` and `192.168.20.1`, respectively. Router interfaces `enp0s3` and `enp0s8` serve these subnets; `enp0s9` serves host-only management; `enp0s10` serves NAT.

## 7. Incident: duplicate cloned machine IDs

### Symptom and investigation

All three VMs initially returned the same `/etc/machine-id`:

```text
c2f45dea8c95415f8c2d3656407e79ef
```

This was consistent with cloned installations inheriting the original identity. The web VM retained the original ID; the database and router VMs received new IDs.

### Risk controls

1. Created recovery snapshots before modification.
2. Verified NetworkManager profiles and addressing before changing identities.
3. Confirmed both database interfaces used `ipv4.method: manual`.
4. Confirmed the router's web, database, and management interfaces used `manual`; NAT used DHCP.
5. Checked router DHCP lease and client identifier.
6. Changed **one VM at a time** and rebooted before moving to the next.

### Commands used on each VM needing a new identity

```bash
sudo truncate -s 0 /etc/machine-id
sudo systemd-machine-id-setup
cat /etc/machine-id
sudo reboot
```

**Caution:** These commands modify a core system identity and should not be run casually on a production host. `systemd-machine-id-setup` can obtain identity from existing sources, so the result must be checked for uniqueness. Plan maintenance, understand application dependencies, and have a tested recovery strategy before use.

### Final machine IDs

| VM | Final machine ID |
|---|---|
| lab-server-1 | `c2f45dea8c95415f8c2d3656407e79ef` |
| lab-server-2 | `dbf74d72345f47b9ab5dcafdb8e5944e` |
| lab-router | `fb8fae4830834466b8e8f625e7f4a9c8` |

On `lab-server-2`, `/var/lib/dbus/machine-id` did not exist; no separate D-Bus identity file was modified. After reboot, database IPs/routes and MariaDB `active`/`enabled` status were unchanged. After router reboot, hostname, four interface addresses, default route, forwarding setting, active zones, and `lab-internet` policy were intact.

## 8. Post-change validation evidence

All tests below were run **from lab-server-1 after both modified VMs rebooted**.

### Cross-subnet connectivity

```bash
ping -c 4 192.168.20.10
```

Result: **4 transmitted, 4 received, 0% packet loss**, average RTT **2.559 ms**.

### Database TCP reachability

```bash
timeout 5 bash -c 'echo > /dev/tcp/192.168.20.10/3306' \
  && echo 'Database port reachable' \
  || echo 'Database port unreachable'
```

Result: `Database port reachable`. This verifies TCP connectivity, **not** database authentication or SQL execution.

### Application HTTP response

```bash
curl -sS -o /tmp/ecommerce-check.html \
  -w 'HTTP status: %{http_code}\n' http://localhost/
grep -Ei 'Drone|Laptop|Tablet|Watch' /tmp/ecommerce-check.html | head -n 8
```

Result: **HTTP 200** and product HTML including Laptop (`100$`), Drone (`200$`), and Tablet (`50$`). This supports application health; no direct SQL query was run in this final check.

## 10. Interview talking points

**Q: What is the difference between free filesystem space and free LVM space?**  
A: `df -hT` reports unused capacity inside a mounted filesystem. `vgs` reports unallocated extents in a volume group. A volume group can have `VFree=0` while its existing filesystems have ample unused capacity.

**Q: How do you verify that a Linux service survives reboot?**  
A: Check `systemctl is-enabled`, reboot under a controlled change, then check `systemctl is-active` and perform an application-level health test.

**Q: Why did you change the cloned machine IDs?**  
A: Each independent Linux installation should have a distinct identity. The cloned VMs shared the same ID, so I created snapshots, checked network dependencies, changed one identity at a time, rebooted, and validated the services and network.

**Q: Why is ping insufficient to prove an application works?**  
A: Ping confirms ICMP reachability only. I also tested TCP port 3306 and checked that Apache returned HTTP 200 with product content.

**Q: What does a default route do?**  
A: It provides a next hop for destinations not covered by a more specific route. Here the web host sends database-subnet traffic to `192.168.10.1`, and the database host returns traffic via `192.168.20.1`.

## 11. Follow-up checks / limitations

- Perform a direct authenticated SQL query from the web tier if deeper DB verification is required.
- Audit firewalld permanent configuration explicitly and verify persistence after further maintenance.
- Validate a snapshot restoration procedure in a disposable clone rather than risking the working environment.
- Consider an independent MariaDB backup, especially before later filesystem or database exercises.
- Record router kernel/package baseline if a complete per-host software inventory is required.
- Check DNS resolution independently if name-based connectivity becomes part of the lab.

## 12. Outcome

This module established a baseline across a three-VM CentOS Stream lab, corrected duplicate cloned system identities, and verified network and application functionality after reboot. It demonstrates Linux administration, LVM inspection, NetworkManager troubleshooting, systemd service validation, firewall/routing analysis, recovery planning, and controlled change management.
