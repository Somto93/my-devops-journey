# Linux Services

This section documents my hands-on learning of Linux services, systemd, and service management using `systemctl`.

To reinforce what I learned, I created a small Python Flask application and configured it to run as a Linux service. I also deliberately introduced problems into the application to practise troubleshooting.

## What is a Linux Service?

A Linux service is a program or application that can run in the background and be managed by the operating system.

On systems using systemd, services can be controlled using the `systemctl` command.

## Service Management Commands

### Start a service

```bash
sudo systemctl start my_app
```

### Stop a service

```bash
sudo systemctl stop my_app
```

### Restart a service

```bash
sudo systemctl restart my_app
```

### Check the status of a service

```bash
systemctl status my_app
```

### Enable a service at system startup

```bash
sudo systemctl enable my_app
```

### Disable a service from starting automatically

```bash
sudo systemctl disable my_app
```

## Understanding Start vs Enable

I learned that starting and enabling a service are different.

`start` runs the service now:

```bash
sudo systemctl start my_app
```

`enable` configures the service to start automatically when the system boots:

```bash
sudo systemctl enable my_app
```

A service can therefore be running without being enabled at startup.

## Hands-on Lab: Running a Flask Application as a Service

To practise Linux service management, I created a simple Flask application.

The application contains two routes and listens for connections on a configured TCP port.

[View my Flask application](./my_app.py)

Before turning it into a service, I ran it manually:

```bash
python3 my_app.py
```

I then tested the application from another terminal using:

```bash
curl http://localhost:8080
```

The application returned:

```text
Welcome!
```

This helped me understand that when I ran the application manually, the terminal remained occupied by the running Python process.

## Creating a systemd Service

I created a systemd unit file called `my_app.service`.

[View my systemd service file](./my_app.service)

The service contains an `ExecStart` instruction that tells systemd which command should be executed to start my application.

After creating or modifying the service file, I used:

```bash
sudo systemctl daemon-reload
```

This tells systemd to reload its unit-file configuration.

I could then manage the application using:

```bash
sudo systemctl start my_app
sudo systemctl stop my_app
sudo systemctl restart my_app
systemctl status my_app
```

## Viewing Service Logs

I used `journalctl` to investigate the logs generated by my service:

```bash
journalctl -u my_app
```

To view only recent entries:

```bash
journalctl -u my_app -n 20
```

To follow new log entries in real time:

```bash
journalctl -u my_app -f
```

## Troubleshooting Challenge: Service Running but curl Failed

As part of my practice, I deliberately changed the port used by the Flask application.

After restarting the service, `systemctl` showed that `my_app` was running successfully.

However, when I tried:

```bash
curl http://localhost:8080
```

I received:

```text
curl: (7) Failed to connect to localhost port 8080: Could not connect to server
```

Initially, this appeared confusing because the service itself was running.

### Investigation

I checked the service:

```bash
systemctl status my_app
```

The service was active.

I then inspected its logs:

```bash
journalctl -u my_app
```

Since the application was running, I needed to determine where it was listening.

I used:

```bash
ss -ltnp
```

This allowed me to inspect the TCP ports currently listening on the machine.

### Root Cause

The application was running correctly, but I had changed the port in the Flask application while still attempting to connect to port `8080` with `curl`.

The client and application were therefore using different ports.

### What I Learned

This exercise taught me that an `active (running)` service does not necessarily mean that a client will be able to connect using any port.

When troubleshooting a similar problem, I can investigate:

1. Is the service running?
2. What does `systemctl status` show?
3. What do the service logs show?
4. Which port is the application actually listening on?
5. Is the client attempting to connect to the correct port?

It also helped me understand the relationship between an application, a systemd service, a running process, and a listening network port.
