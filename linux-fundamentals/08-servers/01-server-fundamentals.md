# Server Fundamentals

## What Is a Server?

A server provides resources, services, or applications to clients over a network.

Different servers can perform different roles within an IT environment.

Examples include:

```text
Web Server
Application Server
Database Server
Email Server
Chat Server
Backup Server
```

In a real application environment, these roles may be distributed across multiple servers.

For example:

```text
Users / Clients
      |
      v
 Web Servers
      |
      v
Application Servers
      |
      v
Database Servers
```

Multiple web servers may communicate with multiple application servers, which then communicate with database servers.

This separation allows different parts of an application architecture to perform different responsibilities.

---

## Web Servers

A web server is responsible for serving web content to clients.

This can include:

```text
HTML pages
CSS
JavaScript
Images
Other static files
```

A client such as a web browser sends an HTTP request to the server, and the server responds with the requested content.

A simple request flow looks like:

```text
Browser
   |
   | HTTP Request
   v
Web Server
   |
   | HTTP Response
   v
Browser
```

One web server used in my practical labs was:

```text
Apache HTTP Server
```

---

## Application Servers

Application servers are used for backend application processing.

Instead of only returning existing static files, an application server can run application logic and generate responses dynamically.

Examples of backend technologies shown in the learning material included:

```text
Java
Python
JavaScript
```

Examples of frameworks included:

```text
Java       -> Spring
Python     -> Flask
JavaScript -> Express
```

During my practical labs, I worked with:

```text
Flask
Express
Apache Tomcat
```

---

## Web Frameworks

A web framework provides tools and structure for developing web applications.

The frontend of a web application may use technologies such as:

```text
HTML
CSS
JavaScript
```

The backend may be written using languages such as:

```text
Java
Python
JavaScript
```

A simplified application flow is:

```text
Frontend
   |
   | Request
   v
Backend Application
   |
   | Processing
   v
Response
```

Frameworks help developers build the backend application that receives requests and produces responses.

## Static Websites

Static websites serve content that already exists as files on the server.

For example:

```text
/var/www/html/index.html
```

A request for that page can be handled by reading the file and returning it to the client.

Conceptually:

```text
Client
  |
  | GET /index.html
  v
Web Server
  |
  | Reads index.html
  v
HTTP Response
```

In the Apache lab, I created an HTML file inside:

```text
/var/www/html
```

Apache immediately served the updated content without requiring a service restart.

This demonstrated that changing a static file is different from changing the server's configuration.

---

## Dynamic Websites

Dynamic websites involve application logic that generates responses while the application is running.

For example, during the Flask lab I created:

```python
@app.route("/health")
def health():
    return {"status": "healthy"}
```

Requesting:

```text
/health
```

caused the Python application to execute the route and return:

```json
{"status":"healthy"}
```

Similarly, the Node.js Express application contained:

```javascript
app.get('/health', (req, res) => {
    res.json({ status: 'healthy' });
});
```

These responses are produced by application code rather than simply returning an existing HTML file.

---

## Static vs Dynamic Content

A simplified comparison is:

| Static Content | Dynamic Content |
| --- | --- |
| Existing files are served | Application code executes |
| HTML, CSS, images, JavaScript files | Responses generated by backend logic |
| Commonly handled directly by a web server | Handled by an application/backend |
| Example: Apache serving `index.html` | Example: Flask `/health` route |

The learning material describes servers hosting static websites as web servers and servers hosting dynamic websites as application servers.

In practice, architectures can combine these responsibilities, but this distinction is useful for understanding the roles introduced in the course material.

## Web Server and Application Server Architecture

A web server and application server can work together.

For example:

```text
Client
  |
  v
Web Server
  |
  v
Application Server
  |
  v
Database Server
```

The web server may handle incoming HTTP requests and static content, while application servers handle backend application logic.

The application server may then communicate with a database server when data needs to be retrieved or stored.

A larger environment might contain:

```text
                 Clients
                    |
          +---------+---------+
          |                   |
          v                   v
     Web Server 1        Web Server 2
          |                   |
          +---------+---------+
                    |
          +---------+---------+
          |                   |
          v                   v
 Application Server 1   Application Server 2
          |                   |
          +---------+---------+
                    |
                    v
              Database Server
```

This introduces the idea that different server layers can be separated and scaled independently.

## Server Software and Running Processes

Installing server software does not automatically mean that the server is currently usable.

During the practical labs, I learned to distinguish between:

```text
Installed software
Running process
Listening network socket
Application response
```

For example, Apache was already installed on the Ubuntu system, but initially it could not start successfully because another web server was already using port 80.

This reinforced an important concept:

```text
Installed != Running != Reachable
```

Each state needs to be verified independently.

---

## Processes

A running server is represented by one or more operating-system processes.

Useful commands for inspecting processes include:

```bash
ps -ef
ps -fp <PID>
pgrep -af <process-name>
```

For example, during the server labs I inspected processes belonging to:

```text
nginx
apache2
java / Tomcat
python / Flask
gunicorn
node
PM2
```

The PID allows a running process to be connected with other evidence such as listening ports.

---

## Ports

Server applications listen on network ports.

Examples encountered during the labs included:

```text
Apache        -> 80
Tomcat        -> 8080, later changed to 9090
Flask         -> 5000
Gunicorn      -> 8000
Node/Express  -> 3000
```

A client normally needs both an address and a port to reach a network service.

For example:

```text
http://127.0.0.1:5000
```

contains:

```text
Protocol -> HTTP
Address  -> 127.0.0.1
Port     -> 5000
```

---

## Listening Sockets

A process must listen on the expected network address and port before clients can connect to it.

A useful command for checking listening TCP sockets is:

```bash
sudo ss -lntp
```

To inspect a specific port:

```bash
sudo ss -lntp | grep ':5000'
```

During the Flask binding experiment, this showed:

```text
127.0.0.1:5000
```

when Flask was configured with:

```python
app.run(host="127.0.0.1", port=5000)
```

This provided operating-system evidence that the application was only listening on loopback.

---

## Binding Addresses

The address a server binds to determines which local interfaces can accept connections for that service.

### Loopback Binding

For example:

```text
127.0.0.1:5000
```

means the application is listening only on the IPv4 loopback interface.

In the Flask lab:

```python
app.run(host="127.0.0.1", port=5000)
```

resulted in:

```text
curl http://127.0.0.1:5000/health
-> worked

curl http://172.23.210.163:5000/health
-> connection failed
```

The application itself was healthy. The problem was that it was not listening on the `eth0` address.

### All-Interface Binding

When Flask was configured as:

```python
app.run(host="0.0.0.0", port=5000)
```

it reported:

```text
Running on all addresses (0.0.0.0)
Running on http://127.0.0.1:5000
Running on http://172.23.210.163:5000
```

Both requests then worked:

```bash
curl http://127.0.0.1:5000/health
curl http://172.23.210.163:5000/health
```

Both returned:

```json
{"status":"healthy"}
```

## HTTP Responses

A successful network connection does not necessarily mean that the requested resource exists.

During the Apache lab:

```bash
curl -I http://localhost/does-not-exist.html
```

returned:

```text
HTTP/1.1 404 Not Found
```

This was important because a `404` proves that an HTTP server was reached and responded.

That is different from:

```text
curl: (7) Failed to connect
```

which indicates that the client could not establish the required connection.

Therefore:

```text
HTTP 404
   =
Server reachable
HTTP response received
Requested resource not found
```

while:

```text
Connection failure
   =
HTTP request could not be completed because
the required connection was not established
```

## Important Troubleshooting Model

The server labs reinforced the following troubleshooting approach:

```text
1. Is the software installed?
          |
          v
2. Is the service/process running?
          |
          v
3. Is the expected port listening?
          |
          v
4. Which process owns the port?
          |
          v
5. Is it bound to the correct address?
          |
          v
6. Can the client establish a connection?
          |
          v
7. What HTTP response is returned?
          |
          v
8. What do the logs show?
```

This helps identify the failing layer instead of immediately changing configuration.

---

## Key Takeaways

- Different server types perform different roles.
- Web servers commonly serve web content.
- Application servers handle backend application logic.
- Static content can be served directly from files.
- Dynamic responses are generated by application code.
- Web frameworks help developers build web applications.
- A running server is ultimately represented by processes and listening sockets.
- IP addresses and ports determine where applications can be reached.
- `127.0.0.1` restricts an application to loopback when used as the listening address.
- `0.0.0.0` can be used to listen across available IPv4 interfaces.
- An HTTP error such as `404` is different from a connection failure.
- Server troubleshooting should be evidence-based: inspect the process, socket, HTTP response, and logs before changing the system.
